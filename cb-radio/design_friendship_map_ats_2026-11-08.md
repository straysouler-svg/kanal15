## 1. Механика дружбы + стрим-интерактив

### Как устроено сейчас

**Дружба — `bonds.py` (весь модуль, 252 строки), читается из `bonds.json` рядом с рацией.**
- Очки 0..255, старт 25 (+6 за каждую прошлую встречу при сидинге, `bonds.py:120-137`).
- Уровни (`bonds.py:23`): 0 «незнакомый» (<35), 1 «знакомый» (35+), 2 «приятель» (60+), 3 «друг» (150+). Порог знакомого поднят 30→35 решением пользователя 2026-11-10.
- Рост: разговор +1/+2 (по имени)/+3 (спасибо, похвала), первый разговор за игровой день +3, кап +15 в день; грубость −25, унижение −15 (`bonds.py:139-156`, вызовы в `cb_radio.py` ~1660).
- Что реально открывают уровни сегодня (всё, что нашёл):
  - уровень 0 → фильтр реплик, где водитель зовёт игрока по имени (`bonds.py:170-171`, `cb_radio.py:733`, `803` в `Deck.draw`, `bond_filter` ~797);
  - уровень ≥2 → «встретимся?» отвечает `meet_yes` (`cb_radio.py:1444`);
  - уровень 3 → друг молчит после грубости в 0.7 раза короче (`bonds.py:246-252`);
  - иначе очки только влияют на настроение (веса выбора реплик `bonds.py:229-239`) и на чипы оверлея `♥♥ 😄` (`bonds.py:241-244`, `overlay.py:110-121`).
- Изменение уровня уже показывается в оверлее (`overlay.bond()`, вид «bond» в `overlay.py:117-120`).
- **Уровни сейчас не открывают контент.** План Steam 2026-11-08 (MODLOG): «уровни дружбы открывают более личный контент» — в коде этого ещё нет.

**Настроение** — отдельная система `bonds.py:174-227` (дневное настроение по md5, сдвиги ±, дрейф назад за 10 мин). С дружбой почти не пересекается — хороший шаблон для новых механик.

### Предложение: модель «личного контента по уровням»

**Вариант А (рекомендую): теги уровня прямо в phrases.json + фильтр в колоде.**
Точка врезки уже существует: `bond_filter`/`Deck.draw` (`cb_radio.py:733, 803`) — тот же паттерн, что у «не зовёт по имени». В phrases.json у реплики появляется необязательное поле `"lv": 2` (или `"min_level"`). Фильтр: `cands = [p for p in cands if level(actor) >= p.min_level]`. Это ~15 строк в cb_radio.py + разметка реплик данными, без новых модулей. Открывается:
- **1 (знакомый):** «как дела»-ответы с именем (уже есть как v_neutral — логично повысить до уровня 1 именно их), первые бытовые истории.
- **2 (приятель):** личные темы — семья, зарплата, здоровье (интенты `family`/`salary`/`health` в `intents.py` уже есть! сейчас отвечает любой). Предлагаю: если адресат на уровне 0–1, он отвечает уклончиво/общо; личный ответ — с 2.
- **3 (друг):** секретные/передоверные сценки, «свои» байки, возможность «дёрнуть друга в эфир» по имени в любое время смены (правило смены остаётся — это фича культуры, а не ограничение дружбы; обсудить).

**Вариант Б: скрытая «личная колода».** У каждого водителя в phrases.json блок `private/`, пополняется редко, тянется только при уровне ≥2. Плюс — контент визуально отделён; минус — дублирует структуру reactions, дороже в поддержке.

**Вариант В (не рекомендую): отдельный json «отношения» с таблицей открытий.** Третий источник истины рядом с bonds.json и phrases.json — лишний.

**Как растёт и падает — оставить как есть, с двумя правками:**
1. Кап +15/день уже защищает от гринда. Дополнительно: очки за разговор давать только за **новые** темы (интенты), повтор одной и той же темы — 0. Это дешёвая проверка (интент уже известен в момент `bond_add`).
2. Падение: сейчас только реактивное (грубость). Добавить медленное затухание: −1 очко за игровые сутки без разговора с этим водителем. Сильно падает не будет (150→на месяц без общения), но «друг, которого не звали месяц» реально остывает. Реализация — в `set_world`/по смене `day` в bonds.py, ~10 строк.

### Стрим-интерактив (зрители влияют на эфир)

**Что уже есть и переиспользуется:**
- Локальный HTTP-оверлей на 127.0.0.1:47823 (`overlay.py`), страницы `/` и `/v`, endpoint `/state` (GET). Рация — единственный хозяин состояния, OBS — только отображает.
- Очередь реплик: в `cb_radio.py` уже есть отложенная очередь `self.pending = (время, "cross", actor, ...)` и система событий (доставки бухгалтерии копятся и озвучиваются раз в 25 мин). Новые «события» ложатся в тот же механизм.
- Уровень «Эфир» (`world.set_air`) — прецедент внешнего воздействия: меняются только частоты, логика не ломается. Стрим-события должны следовать тому же принципу.

**Вариант А (рекомендую): опросный диспетчер через тот же оверлейный сервер.**
- Добавить в overlay.py endpoint `POST/GET /poll` (state: вопрос, варианты, голоса, дедлайн). Голосование — сторонний бот (Nightbot/StreamElements для Twitch/YouTube, отдельный Telegram-бот), который пишет голоса в рацию... нет, бот не может писать в рацию. Реалистичнее: рация сама раз в N секунд читает файл `stream_events.jsonl` (или принимает POST от маленького локального мостика). **Простейшая схема без новых зависимостей:** оверлейный сервер слушает 127.0.0.1 и принимает POST `/event {type:...}`; маленький скрипт-мост (50 строк) читает чат Twitch/YouTube через IRC/WebSub и шлёт события в рацию. В рации очередь событий разгребается между репликами.
- Что может делать зритель (по нарастанию трудности):
  1. **Опрос «кого позвать»** — рация считает голоса 60–120 с и при ближайшей `schedule_meeting` берёт не случайного, а выбранного (вес в `random.choices` уже есть — `world.py:346-347`, меняется на бесконечный вес для избранного, пока событие живо). ~30 строк.
  2. **Зритель-диспетчер** — один раз за стрим зритель через донат/очередь может «поручить» рейс: создаётся встречный с конкретным грузом из биржи (`world.real_offer` уже есть). ~40 строк.
  3. **События донатов** → одноразовые события: «заказ песни» (интент `song` уже есть — пустить сильнее в колоду), «попроси анекдот», «все здороваются с новым» (boost гритинга), «долгая тишина/гудки» (новый звуковой fx). Каждое — короткая реакция на событие + 1–2 реплики, переиспользуют существующие пулы.
- Донаты как триггер — именно то, что двигает план «бюджет копится из донатов» (MODLOG 2026-11-08). Первым делом делать №1 (опрос) — он самый дешёвый и самый зрелищный.

**Вариант Б: полноценная интеграция с Twitch API в рации.** Не рекомендую: токены, OAuth, ревью-риски, лишняя сеть в монолите. Мост — отдельный процесс, рация остаётся офлайн-дружелюбной.

**Открытые вопросы:**
- Трибун зрителя: один голос на человека или вес от доната? (риск pay-to-win в атмосфере — рекомендую донат = украшение, не вес).
- Опросы: зрители выбирают из «кто сейчас в зоне» (атмосферно честно) или из всех (может выбрать спящего)?
- Должны ли уровни дружбы влиять на ответы зрителю в чате (через оверлей-текст)?

**Трудоёмкость (грубо, код):** модель контента по уровням (А) — 1–2 дня код + разметка реплик; стрим-опрос — 1 день; диспетчер/донаты — 2–3 дня; озвучка новых реплик — отдельно по прайсу ElevenLabs.

## 2. Новые страны / DLC: конвейер данных

### Как устроено сейчас

- Единственный источник карты — `map/cities_full.json`: 382 города, формат `{name, country, x, z, src, population}`; `src` ∈ {verified (74), confirmed (45), fit (263)}. Координаты — мировые метры телеметрии ETS2.
- Дороги **не хранятся**: `world.Roads` (`world.py:36-47`) строит k=4 ближайших соседа (max_link 26 км), затем `_join_components` (`world.py:66-78`) соединяет компоненты ближайшей парой (это и есть «поромы»). Путь — Дейкстра (`world.py:80-101`).
- Ограничение по DLC — `world.restrict_to(owned)` (`world.py:502-528`): города берутся из компаний сохранения игрока (`company.cities` из сохранения, `company.py:105`), страны держатся целиком, города без компаний (`no_company`) выживают, если их страна куплена.
- `world.ok = len(cities) > 50` (`world.py:137`) — мягкий детект.
- Валидация сети сейчас **нет** (кроме `_join_components`); check_air проверяет звук, не карту.
- Происхождение городов: `map/extracted/` (есть папка), `city_geo.json`, `cities_jagfx.json`, `city_list.py`, `cities_unverified_backup.json` — следы ручного/полуручного конвейера. Как именно `cities_full.json` собирался — в коде не восстановил (нет скрипта сборки; вероятно, ручная работа + инструменты в map/).

### Предложение: конвейер «страна как данные»

**Формат остаётся `cities_full.json` (не плодить схемы), но добавляем `map/validate_map.py` и `map/update_map.py`:**

1. **Источники городов новой страны:** (а) официальный def DLC — распаковать `tools/scs_extractor`, из `def/world/*.sii` берутся реальные координаты узлов (точность ~verified); (б) карты координат сообщества (jagfx, координаты уже использовались — `cities_jagfx.json`); (в) ручное добавление «fit» — текущий дефолт.
2. **Автоматически должно обновиться:** `cities_full.json` (новые токены), счётчик/детектор (`world.ok` порог поднимется сам), список стран где-нибудь в акторах (lanes — нет, lanes фильтруются `world.py:149`). Hazards и state переживают: `_load` (`world.py:730-741`) уже отбрасывает маршруты с неизвестными городами.
3. **Вручную:** population (можно оценкой), разметка `no_company`, lanes водителей (если хотим новые страны в «куда едешь?»), тексты с упоминанием новых стран, проверка «verified» выборочно вживую.
4. **Валидация (`map/validate_map.py`):**
   - связность: `_join_components` не должен создавать «поромы» длиннее разумного (сейчас лимит не проверяется!) — отчёт по компонентам до/после;
   - дубликаты по координатам (<1 км);
   - страна присутствует в списке разрешённых (`restrict_to` берёт country из json — опечатка в country сломает ограничение DLC);
   - граф: средняя/максимальная длина ребра, количество «висючек»;
   - smoke-тест: `Roads.path` из 20 случайных пар городов новой страны до 20 пар существующих — пути должны находиться.
5. **Краевой случай, о котором стоит знать:** `restrict_to` решает, какая карта у игрока, по компаниям в **его сохранении**. Новая страна появится у водителей автоматически через 85% реальных рейсов (`world._new_job` → `real_offer`) — но только когда у игрока куплен DLC (компании появятся в сохранении). Ручного кода для «включить страну» не нужно вообще — это следствие данных.

**Альтернатива (отклонена):** настоящая графовая сеть дорог из def-файлов вместо k-NN. Точнее, но: объём данных вырастет в разы, придётся переписывать Roads/_on_my_way/schedule_meeting. k-NN на 382 городах работает честно (проверено вживую, MODLOG 2026-11-04) — не трогаем.

**Открытые вопросы:**
- Откуда брать координаты: есть ли у нас рабочий скрипт распаковки def→координаты (в map/extracted есть что-то, надо смотреть)? Или принимаем подход «jagfx + ручная правка»?
- Порог `world.ok > 50` — оставить или считать от доли стран?

**Трудоёмкость:** конвейер update+validate — 1–2 дня; добавление одной страны данными — часы (при готовых координатах).

## 4. Чатрулетка (проект; реализация НЕ начата, 2026-11-08)

Идея пользователя: рация случайно соединяет двух живых игроков в эфир, если оба едут примерно по одним
дорогам в радиусе действия рации. Чат-рулетка по геопозиции: каждый на своём компьютере, в своей игре,
слышит «другого дальнобойщика» рядом. **Решение: сейчас не выполняем — только проект и точки расширения.**

### 4.1 Матчмейкинг: рандеву-сервер

- **Модель:** крошечный рандеву-сервер (WebSocket, один процесс на VPS 1 CPU/512 МБ). Рация клиента
  раз в ~15 с шлёт **гео-ячейку** (не точные координаты): округлённый хэш ячейки ~5×5 км мира ETS2
  + направление (курс 8 румбов) + скоростной флаг (едет/стоит). Сервер хранит «комнаты» = ячейки;
  два клиента в одной ячейке (или соседних, с учётом курса) → матч.
- **Приватность:** точные x/z игрока никогда не покидают его ПК. На сервере — только ячейка и
  одноразовый псевдоним сессии (например «Проезжий 7»); никаких Steam ID, никакой истории позиций
  (сервер забыт через N минут неактивности). HTTPS/WSS обязателен.
- **Opt-in:** по умолчанию выключено. Включение — config `"roulette": {"enabled": true, ...}` +
  согласие при первом включении (текст про живых людей и правила). Детский/токсичный риск закрывается
  мьютом (см. 4.4).
- **Голос P2P:** сложный путь — WebRTC, требует TURN-сервер (~10–20 $/мес за малый VPS) и большой
  код. Рекомендация: первая версия вообще без голоса (см. 4.2), голос — отдельный этап.

### 4.2 Что передавать (минимальная версия — «телеграф»)

Первый релиз чатрулетки — **не голос, а текстовый протокол поверх эфира**:

- Клиент игрока А распознаёт его PTT-фразу (Whisper уже есть!) и шлёт **текст реплики** серверу;
  рация игрока Б получает её и **озвучивает у себя движком рации** — проезжий «peer» отвечает текстом Б
  той же дорогой. Игроки разговаривают голосом у себя, слышат друг друга через синтез — в духе рации,
  без WebRTC вообще.
- События: `presence` (вошёл/вышел из зоны), `line` (текст реплики + эмоция-разметка по желанию),
  `mood` (необязательно), `bye`. Всё маленькое JSON-сообщения через тот же WebSocket.
- Задержка: распознавание (~1–2 с) + доставка + синтез — в эфире рации это ощущается как
  «дальнобойщик отвечает не сразу», атмосферно терпимо.
- Оценка сложности голоса PTT-релеем (WebRTC + VAD + шум рации): 2–3 недели, плюс TURN-стоимость.
  Текстовый «телеграф»: 3–5 дней на клиентскую часть.

### 4.3 Встройка в существующий мир

Рабочая концепция — **peer как особый актёр**:

- Новый тип водителя в `world.py`: `Driver` с ключом вида `peer:<session>` (не в phrases.json,
  не в `World.drivers` персонажей — отдельный словарь `world.peers`), позиция = ячейка матча,
  скорость приблизительная. Зона слышимости, помехи по расстоянию (`degrade()` в `cb_radio.py`),
  мурмурирование на краю — всё переиспользуется как есть.
- Очередь событий: механизм `self.pending` (отложенные реплики) уже есть; события сервера
  (пришла реплика, peer вошёл/вышел) кладутся туда же — рация остаётся единственным хозяином эфира.
- Реплики peer'а идут через тот же `Player.file()`; синтез peer-текста — локальный (Silero уже
  стоит у пользователей? нет — только у разработчика; **открытый вопрос**: поставлять ли маленький
  локальный TTS, это +30–60 МБ к установщику, либо озвучивать заранее записанными «радиограммами»
  — тогда peer говорит шаблонами, а не дословно).
- Оверлей (`overlay.py`): peer показывается как «Проезжий» с пометкой живого игрока; субтитры его
  реплик — дословно (текст же известен) — красивый плюс для стримов.

### 4.4 Офлайн-деградация и антитоксичность

- **Нет сервера / нет сети / opt-out:** рация ведёт себя ровно как сейчас. Весь код чатрулетки —
  за одним флагом `cfg["roulette"]["enabled"]` и одним фоновым потоком; его отсутствие не меняет
  ни одного пути колоды/мира. Сценарий «сервер лёг» = молчание рации оставляет без изменений.
- **Антитоксичность:** кнопка «Выключить чатрулетку» (в трее, рядом с «Эфиром») — мгновенный выход
  из комнаты и стоп сессии; «Пожаловаться» шлёт на сервер флаг сессии (без записи переговоров);
  повторные жалобы → серверная блокировка псевдонима. Никакой персистентной идентификации игроков.
- **Стоимость сервера:** рандеву + ретрансляция текста — килобайты в секунду на пару; VPS за 3–5 $/мес
  держит сотни одновременных пар. Голос (этап 2) меняет математику → тогда смотреть TURN/самостоятельный
  signaling.

### 4.5 Точки расширения, которые стоит оставить СЕЙЧАС (только документация, кода нет)

1. `world.py`, класс `Driver` — при реализации добавить `peer`-флаг (поле `is_peer`), чтобы
   `schedule_meeting`/`update()` могли отличать живого проезжего; сейчас ничего не мешает — класс
   не меняем.
2. `cb_radio.py`, очередь `Operator.pending` — формат кортежа `(время, group, kind, prefer, who)`
   уже универсален; событиям peer'а хватит нового `group == "peer"` без перекройки очереди.
3. `cb_radio.py`, `bonds.py` — peer НЕ должен писаться в bonds.json (дружба только с персонажами):
   в `Bonds.add()` уже стоит защита от «лишних» ключей — при реализации peer-ключи начинаются с
   `"peer."`, аналогично защищённым `"driver."`.
4. `config.json` — зарезервировать (документированно, без кода) секцию `"roulette": {"enabled": false,
   "server": "", "cell_km": 5}`; парсить её начнём при реализации.
5. `overlay.py` — вид строки «Проезжий» уже есть (`kind: "foreign"`); peer-строки пойдут отдельным
   видом, страница меняется минимально.
6. `gamecheck.py` — правило «рация без игры не работает» касается и peer-режима; серверное
   подключение стоит поднимать только при живой телеметрии (тот же паттерн, что и сейчас у компании).
