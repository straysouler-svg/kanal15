# Правила работы с проектом «Грузовички»

## Карта проекта

- `cb-radio/` — рация «Канал 15»: Python, телеметрия ETS2, речь, персонажи и установщики.
- `build/radio.spec` — сборка `CB-Radio.exe` через PyInstaller.
- `promo/shorts/` — действующий конвейер Shorts; `promo/design/Channel15_Design_Pack/` — локальный пакет новой айдентики, до одобрения пилота не заменяет текущий стиль.
- `drivetrain/`, `haze/`, `reshade/`, `simhub/` — отдельные модификации и настройки ETS2.
- `README.md` — публичная витрина GitHub (утверждённый текст, «программа-компаньон», не «мод») + карта проекта внизу; `MODLOG.md` — решения, живые проверки и инциденты.
- `.kimi-code/skills/kanal15-*/SKILL.md` — специализированные регламенты рации. Перед работой прочитать подходящий: кодинг, голоса, тексты, озвучка или релиз.

## Порядок работы

1. Сначала факты, потом правка: изучить логи, данные, соответствующий код и `git diff`. При цепочке ошибок сначала разобрать первую — последующие могут быть её следствием.
2. Сохранить чужие незакоммиченные изменения. Не откатывать и не перезаписывать их, не исправлять посторонние проблемы «заодно».
3. Делать один прицельный фикс за раз. Если одинаковая логика обнаружена в нескольких местах, по возможности исправить её через общую точку, а не размножать расходящиеся копии.
4. Перед крупной правкой `cb-radio/cb_radio.py` создать рабочую копию `cb_radio.before_<что>.py`. Рефакторинг монолита и изменение архитектуры сначала согласовать с пользователем.
5. Перед изменением обращения к внешнему API свериться с официальной документацией. Не расходовать платные лимиты на отладку: сначала локальные проверки функций с сохранёнными ответами или заглушками.
6. Основной агент действует оркестратором по назначению пользователя. Запускать только нужных специалистов в рамках его задач и параллелить лишь независимые части. Регламенты кодера, тестировщика и автора находятся в `.claude/agents/`; остальные роли задаются в prompt до оформления отдельными файлами.

Для нетривиальных изменений кода использовать цепочку `developer → tester`: tester проверяет реальный diff и не правит исходники, а замечания возвращаются developer через оркестратора. `scene-writer` работает сначала в черновиках; интеграция в эфир и озвучка — только после одобрения текстов пользователем. Все специалисты возвращают отчёты оркестратору, а пользователь получает сводный результат.

## Экономия токенов

Токены — ограниченный ресурс, пользователь явно требует беречь их. Правила:

- Штурман сам отвечает на простые вопросы и делает 1–2 чтения файлов без субагента.
- Субагент запускается только когда нужен свежий контекст, независимая проверка, большой объём чтения или специализированная работа.
- Не дробить одну задачу на множество агентов, если каждому придётся заново читать одни и те же документы. Для автора — один запуск на весь состав персонажей, а не отдельный агент на персонажа.
- Модели субагентов задаются пулом `[secondary_model]` в `~/.kimi-code/config.toml`: рабочая лошадка — `kimi-code/kimi-for-coding`; `kimi-code/kimi-for-coding-highspeed` — только мелкие срочные проверки (дороже за токен); `kimi-code/k3` — только сложная архитектура, тяжёлая отладка или итоговое рискованное решение.
- Публикации, сообщения от имени пользователя, платная генерация и необратимые действия — только после явного согласия.

## Границы безопасности

- Чтение логов, поиск по коду, `git status` и `git diff` можно выполнять сразу.
- Удаление данных, сброс изменений, `git commit`/`push`, публикация файлов и другие внешние или труднообратимые действия — только после явного разрешения пользователя.
- Платную генерацию через ElevenLabs/OpenRouter запускать только по запросу пользователя; сначала проверить остаток и озвучивать лишь нужные реплики.
- Никогда не читать и не печатать секреты (`*_key.txt`, токены, `.env`). Их должны читать сами штатные скрипты.
- Не экспериментировать с живыми `state.json`, `world_state.json`, `bonds.json`: использовать копии. Инцидент: замер на живом состоянии извлёк 20 реплик из колоды, их пришлось восстанавливать вручную.
- Не запускать `tools/gen_level3.py` для обновления текущего эфира: он перезапишет `audio/level3`. После `remix.py` проверить голос Ласточки: скрипт может вернуть Laura вместо выбранного варианта.
- Не убирать ограничения `OPENBLAS/OMP/MKL_NUM_THREADS=1` из `cb_radio.py`: без них numpy/scipy резервируют около 1,2 ГБ на потоки.
- Не менять проверенные вживую смещения телеметрии по памяти или чужой документации. После изменения штрафов проверить источники RenCloud и SimHub.
- `cb-radio/config.json` содержит локальные настройки: не включать их в коммит без отдельной необходимости.

## Проверка результата

- Изменение не считается завершённым, пока не пройдены относящиеся к нему штатные проверки и исходный сценарий пользователя. Нельзя выдавать запуск импорта или компиляцию за полноценную проверку.
- Для эфира запустить `venv\python tools/check_air.py` из `cb-radio/`; ожидаемый результат — «проблем нет».
- Для прослушки без игры использовать `cb_radio.py --listen [actors]`, для тангенты — `--ptt-test`.
- Для собранной рации выполнить `release\<variant>\CB-Radio\CB-Radio.exe --selftest`; правила версий и установщиков — в навыке `kanal15-release`.
- Если живая проверка в ETS2 невозможна, прямо указать это и не утверждать, что поведение проверено.
- После проверок посмотреть `git status`; удалить только созданные этими проверками ненужные артефакты, не трогая остальные файлы.

## Память проекта

- При старте сессии сначала читать `STATUS.md` — там текущее состояние (версия, каналы, квоты, черновики на одобрении, открытые задачи). `MODLOG.md` — архив истории, читать целиком НЕ нужно, открывать только по конкретному вопросу. Это прямое требование пользователя ради экономии токенов.
- `STATUS.md` обновлять при каждом значимом изменении состояния (релиз, квоты, новые черновики, смена плана) — коротко, в конце работы над задачей.
- Значимые решения, живые замеры и новые инциденты фиксировать в `MODLOG.md`: проблема, причина, решение, проверка и источник, если он есть. `MODLOG.md` — только про рацию «Канал 15»; записи других проектов воркспейса живут в `backup/MODLOG_other_projects.md`.
- После нового инцидента добавлять сюда только устойчивое правило: когда срабатывает, что делать, почему и как проверить. Не превращать файл в потоковый дневник.
- Версии менять через `cb-radio/tools/bump_version.py`; релизные изменения отражать в `cb-radio/CHANGELOG.md`.
- Если правила или команды в этом файле устарели, обновить его вместе с изменением проекта.
